1 / 10 — Проблема

Смена тонет в бумаге

  • Наряды на бумаге теряются, статусы узнают по телефону.
  • Авария ждёт: непонятно кто занят, где простой, что просрочено.
  • Сдача без фото и шифров → повторные выезды и споры.
  • Итог: потери смены — время мастера, простои, повторные отказы.
2 / 10 — Решение

НарядAI: один цикл на всех

  • Роли: worker (исполнитель), master (мастер), manager (руководитель), admin (админ).
  • Цикл: issued → accepted → in_progress → done → ai_review → closed, ветки queued / paused / rework / rejected / cancelled.
  • Мастер выдаёт за минуты, рабочий видит задачу сразу, руководитель — смену целиком.
Выдать → Принять → Выполнить → Сдать → Проверить → Закрыть
3 / 10 — Живой сценарий

7 минут: от аварии до закрытия

  • Выдача: мастер создаёт наряд: участок, оборудование (можно по QR), приоритет critical.
  • Принятие: рабочий получает уведомление, жмёт Принять → Начать. Доска мастера обновляется сама.
  • Сдача: текст работ + шифр + материалы + фото «после». Внеплан без фото не сдаётся.
  • Проверка: ИИ даёт verdict/score, мастер нажимает «Согласен» → closed, либо возврат в rework.
4 / 10 — Архитектура

Сервер — арбитр, клиент — PWA

  • Бэкенд: FastAPI + PostgreSQL (транзакции, неизменяемый журнал) + Redis (фон/кэш) + S3 (фото, приватный бакет, signed URL 300 с).
  • Клиент: React PWA (Vite, manifest + service worker) + Tauri-обёртка, сборки Web и Android.
  • Realtime: WebSocket + transactional outbox + фоновые воркеры; пропуск seq → перезапрос экрана.
  • Офлайн: очередь IndexedDB, все POST с Idempotency-Key, повтор тем же ключом — без дублей.

Контракт: FRONTEND_CONTRACT.md (10 разделов) + backend README. Кнопки только из allowed_actions.

5 / 10 — ИИ

ИИ советует, решает мастер

  • Подсказки: топ-3 исполнителя, шифр по описанию, проверка отчёта.
  • Вердикты: accepted / accepted_with_remarks / needs_rework / needs_master_review; score 0–100, confidence, checks: completeness, relevance, materials, timing, photos.
  • needs_rework сам уводит наряд в rework; закрывает только мастер (agree_ai / override).
  • Mock-профиль без ключей: локальные правила работают сразу. External: Estimin3n на ноутбуке либо Gemini + Groq на сервере.
6 / 10 — Аналитика

Видно, где болит

  • Рейтинг исполнителей: качество + сроки + доля возвратов + объём закрытых + отклонения. Нужно от 5 закрытых нарядов.
  • Тренды, простои, материалы, повторные отказы (пример: Конвейер К-3, подшипник М-02).
  • Инсайты с уверенностью и кнопкой «создать плановый наряд».
  • Экспорт XLSX/PDF: async-отчёт: запрос → 202 job_id → signed_url.
7 / 10 — Безопасность

Доверяй, но проверяй на сервере

  • RBAC на сервере: скоупы worker/master/manager/admin; фронт-роутинг — только UX.
  • Вход по логину и PIN (4–8 цифр), 5 ошибок → 423 account_locked.
  • Конфликт переходов → 409 invalid_transition, кнопки только из allowed_actions.
  • Аудит действий, мягкие удаления, фото в приватном бакете, единый формат ошибок без stack trace.
8 / 10 — Эффект

Что меряем в пилоте

  • Методология: один участок, замеры до/после: время выдачи, реакция на аварию, часы простоя, повторные неисправности за 7 дней, полнота сдачи.
  • Пилот: seeded dev: 4 участка, 25 единиц оборудования, 600+ нарядов за 90 дней + 3 свежих плановых.
  • Качество кода на 14.10 (самоотчёт): backend 686 тестов, покрытие 95.4% lines / 91.5% branches; frontend 510 unit + 122 E2E.
9 / 10 — Границы честно

Чего нет — не прячем

  • FCM нет: уведомления только in-app + WebSocket (так в контракте).
  • E2E на моках: 122 сценария через перехват api/v1, не живой стенд.
  • Физические телефоны в этом прогоне не гоняли; прод-домен не проверялся.
  • Техдолг: строгий backend-линт и типизация вне жёсткого гейта.
